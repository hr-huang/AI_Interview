# 企业岗位胜任力报告重构设计

## 1. 目标

把当前“展示评分结果的报告”重构为企业可以直接用于招聘决策和结构化复试的岗位胜任力报告。

本轮同时覆盖：

- 真实评估链路的后端报告契约与生成逻辑；
- 真实报告前端的信息结构与交互；
- 零 API 冻结学生演示数据；
- 演示入口对真实报告组件的复用。

本轮不接入 RAG、向量数据库、自动岗位资料搜索或多岗位扩展。这些能力在报告闭环稳定后独立建设。

## 2. 已确认的产品边界

### 2.1 报告受众

本轮报告只面向企业招聘方，包括 HR、业务面试官和招聘负责人。

“候选人成长建议”不再出现在企业报告中。后续如需候选人反馈，将基于同一评估事实生成独立、可分享和可脱敏的候选人版本。

### 2.2 真实链路与演示链路

真实报告和演示报告必须使用相同的数据契约、后端组合规则和前端组件。

```text
真实 JD + 真实简历 + 动态面试
                ↓
统一评分事实与企业报告组合器
                ↓
统一报告 API 与前端

冻结 JD + 冻结简历 + 冻结问答证据
                ↓
同一评分事实与企业报告组合器
                ↓
同一报告 API 与前端
```

演示链路只在输入是否冻结、是否调用模型方面不同，不允许维护第二套报告文案或页面。

## 3. 方案选择

### 方案 A：只修改前端文案

无法修复后端生成的机械建议、结论冲突和错误证据摘录，拒绝采用。

### 方案 B：真实报告和演示报告分别实现

容易产生“演示结果很好、真实结果很差”的双轨系统，拒绝采用。

### 方案 C：统一企业报告契约与组合器

后端输出企业决策所需的结构化事实，真实和演示共用报告视图。这是本轮采用的方案。

## 4. 后端架构

现有可信评分链保持不变：

```text
Evidence
→ RubricMatch
→ RequirementAssessment
→ ScoreEngine
```

评分完成后新增企业报告组合阶段：

```text
ScoreSnapshot + RequirementAssessment + Evidence + ClaimVerification
                              ↓
EnterpriseReportAssembler
  ├─ CandidateOverview
  ├─ HiringDecision
  ├─ OverallAssessment
  ├─ DecisionSignal
  ├─ ReinterviewPlan
  ├─ EvidenceExcerpt
  └─ ReportConsistencyGuard
                              ↓
AssessmentReport / ReportViewModel
```

`EnterpriseReportAssembler` 只组合和解释已有评估事实，不重新评分。

## 5. 报告数据契约

### 5.1 CandidateOverview

企业报告应包含可独立流转的候选人与岗位上下文：

- `candidate_id`：候选人匿名编号；
- `candidate_name`：允许为空；
- `target_role`：应聘岗位；
- `education_summary`：学历摘要；
- `experience_summary`：项目、竞赛和实习摘要；
- `jd_focus`：本次 JD 的核心要求；
- `interview_rounds`：完成的问答轮数；
- `generated_at`：报告生成时间。

本轮不要求新增候选人数据库；字段从现有简历画像、评估记录和面试状态中组合。缺失信息必须显示为“未提供”，不能臆造。

### 5.2 HiringDecision

招聘结论使用结构化枚举：

- `PROCEED`：建议进入结构化复试；
- `CONDITIONAL_PROCEED`：有条件进入结构化复试；
- `INSUFFICIENT_EVIDENCE`：证据不足，暂缓岗位判断；
- `NOT_RECOMMENDED`：当前证据不支持推进。

字段包括：

- `decision`；
- `decision_label`；
- `provisional_score`；
- `confidence`；
- `conditions`：推进前或复试中必须验证的条件；
- `decision_reasons`：最多三条直接支持该结论的事实。

分数可以保留，但必须与置信度同时展示。低置信度时必须标记为“暂定分数”。

### 5.3 OverallAssessment

候选人专属总评必须回答：

1. 候选人当前达到什么岗位成熟度；
2. 已证明的最强能力是什么；
3. 当前最大的能力风险是什么；
4. 能够承担什么范围的工作；
5. 哪些结论仍未验证；
6. 为什么建议推进、条件推进或暂缓。

总评必须引用结构化评分事实，不允许使用“总体表现良好”等无候选人差异的空泛模板。

### 5.4 DecisionSignal

报告只输出招聘决策真正需要的信号：

- `strengths`：最多三项已验证优势；
- `risks`：最多三项已发现的风险或限制；
- `unknowns`：最多两项影响决策的未验证区域。

每个信号包含：

- 企业可读的标题；
- 一段事实结论；
- 关联维度；
- 支持或限制证据编号；
- 置信度。

“未验证”必须进入 `unknowns`，不得解释为“未发现风险”。

### 5.5 ReinterviewPlan

企业复试计划最多选择三个重点，不再对全部六维机械生成建议。

优先级规则：

1. 岗位门槛维度存在未满足、限制证据或低置信度；
2. 低分维度；
3. 未验证但权重较高或影响岗位发布条件的维度；
4. 关键简历声明仍未核验；
5. 非门槛且证据充分的高分维度不进入复试计划。

每个复试重点包含：

- `priority`；
- `dimension_id` 与企业可读名称；
- `reason`：为什么必须验证；
- `question`：建议主问题；
- `follow_ups`：一到两个追问；
- `positive_signals`：通过信号；
- `risk_signals`：风险信号；
- `pass_criteria`：企业可观察的通过标准；
- `suggested_minutes`；
- `related_evidence_ids`。

问题生成可使用现有结构化模型调用，但重点选择、数量限制和事实边界必须由确定性规则控制。模型失败时使用维度专属的确定性回退内容，禁止六维复用同一句模板。

### 5.6 EvidenceExcerpt

证据抽屉不再重复完整原回答。每条证据包含：

- `conclusion`：该证据支持或限制的结论；
- `quote`：来自候选人原回答的连续关键片段；
- `interpretation`：为什么该片段支持此结论；
- `limitation`：这条证据尚未证明什么；
- `turn_id`：完整问答位置。

`quote` 必须能在对应原回答中找到。冻结观察、演示说明和系统元数据不得作为候选人证据摘录。

完整问题和回答只在“完整面试记录”中展示。

## 6. 一致性保护

`ReportConsistencyGuard` 在报告发布前执行以下规则：

- 已验证维度少于总维度时，不得出现“全部能力均已验证”；
- 存在未验证维度时，必须至少输出一个 `unknown`；
- 存在低分门槛维度、限制证据或低整体置信度时，不得输出“主要风险未发现”；
- 低整体置信度时，`PROCEED` 自动收敛为 `CONDITIONAL_PROCEED` 或 `INSUFFICIENT_EVIDENCE`；
- 未满足岗位匹配发布条件时不得发布数值匹配分；
- 证据摘录无法在原回答中定位时，拒绝发布该摘录；
- 复试重点数量必须为一到三项，除非结论为 `PROCEED` 且没有待核验项，此时允许为空。

一致性检查失败时，真实链路进入报告生成失败状态并保存可审计错误；冻结演示测试必须直接失败，不能静默展示矛盾报告。

## 7. 前端信息结构

报告页面按企业决策顺序组织：

1. 候选人与岗位摘要；
2. 招聘结论、暂定匹配分和置信度；
3. 候选人专属总评；
4. 已验证优势、主要风险和待核验区域；
5. 能力雷达与六维摘要；
6. 企业复试计划；
7. 完整面试记录；
8. 报告说明与审计信息。

### 7.1 删除与合并

- 删除独立的“为什么得到这个评价”六维平铺区；
- 雷达点和维度表成为维度评分详情的唯一入口；
- 证据抽屉只展示关键摘录、解释、限制和完整问答跳转；
- 完整回答只出现在完整面试记录；
- 删除企业报告中的候选人成长建议；
- 不向企业显示 `Requirement`、`RubricMatch`、criterion ID、内部 evidence ID 和英文开发标签。

### 7.2 雷达详情

保留现有常驻双波光晕、键盘操作和移动端适配。点击维度后展示：

- 该维度结论；
- 分数或未验证状态；
- 置信度；
- 一到三条关键证据；
- 限制和未知项；
- 跳转完整问答。

## 8. 演示输出

冻结学生案例继续使用真实确定性评分链，并改由新企业报告组合器生成报告。

预期演示结论必须忠实反映当前事实：

- 五个维度已验证，一个维度未验证；
- Context、RAG、Memory 与工具工程证据较弱；
- 成本、性能与持续优化未验证；
- 整体置信度低；
- 结论为“有条件进入结构化复试”，不是无条件推进；
- 复试计划只选择最关键的两到三个缺口；
- 所有证据摘录均来自冻结回答原文；
- 演示不调用任何外部模型。

演示前端只保留“演示示例、冻结数据、零 API 费用”的来源提示，其余组件与真实报告完全一致。

## 9. 模型与确定性规则边界

确定性代码负责：

- 招聘结论枚举；
- 低置信度和未验证处理；
- 复试重点排序和数量；
- 分数是否允许发布；
- 证据引用与摘录可定位性；
- 所有一致性检查。

结构化模型负责：

- 把评分事实表达为自然、专业的企业总评；
- 在限定维度、事实和目标内生成复试主问题与追问；
- 把规则命中转译为企业可读的正向和风险信号。

模型不得新增候选人经历、改变分数、改变结论枚举、隐藏未验证项或生成无法追溯的证据。

## 10. 测试与验收

### 10.1 后端

- 总评必须包含候选人的强项、风险和未知项；
- 低置信度加未验证维度必须得到条件推进或证据不足结论；
- 不允许“5/6 已验证”与“六维均有证据”同时出现；
- 复试计划只包含一到三个高优先级重点；
- 不同缺口生成不同的复试问题和通过标准；
- 证据摘录必须是原回答子串；
- 模型调用失败时回退内容仍然维度专属；
- 冻结演示保持零 API 且通过一致性校验；
- C01–C06 内部校准定义不得被演示改写。

### 10.2 前端

- 企业总评、优势、风险和未知项均可见；
- 雷达详情不重复完整回答；
- 页面不存在独立六维“为什么得到评价”平铺区；
- 企业复试计划最多三项并展示问题、信号、标准和用时；
- 完整面试记录仍可审计；
- 真实 API 和演示 API 渲染同一组件；
- 桌面和移动端无重叠、横向溢出和不可点击元素；
- 键盘和 reduced-motion 行为保持可用。

### 10.3 比赛展示验收

路演时应能在三分钟内演示：

1. 企业提交 JD 与候选人简历；
2. 智能体根据回答动态追问；
3. 报告给出有条件、可解释的招聘结论；
4. 点击雷达查看证据摘录与限制；
5. 企业直接获得下一轮结构化复试计划；
6. 展示完整面试记录和审计边界。

## 11. 后续阶段

本轮完成后再建设时效性知识链：

```text
最新岗位资料搜索与采集
→ 清洗、去重、来源审计和版本化
→ 向量数据库
→ 检索与重排
→ 出题材料和 Role Pack 更新候选
→ 人工或规则审核
→ 发布新岗位标准版本
```

RAG 只提供岗位知识、题目场景和能力标准更新依据，不直接参与候选人评分。
